# Задание 2: индекс и единое правило открытых заявок

Это проект решения, без изменения Python, XML или базы данных.

## Индекс

В `models/request.py` сохранить свойства поля и добавить индекс:

```python
planned_from = fields.Datetime(string="Окно с", required=True, index=True)
```

Обычный B-tree подходит для диапазона `>= start`, `< end` и сортировки по времени.
Не предлагаю пока составной или частичный индекс: сначала нужны планы запросов
и распределение реальных данных. На 50 записях последовательное сканирование
может быть оптимальным даже при наличии индекса.

## Единый метод модели

Добавить в `tucha.request` следующий метод (пример, не реализация):

```python
@api.model
def _open_requests_domain(self, start, end):
    return [
        ("active", "=", True),
        ("stage", "not in", ("completed", "cancelled")),
        ("planned_from", ">=", start),
        ("planned_from", "<", end),
    ]
```

`start` и `end` — обязательные
naive datetime в UTC, как серверные Datetime Odoo; вызывающий код передаёт
`start < end`. Возвращается новый список условий ORM domain, без поиска,
`sudo()`, изменения контекста, лимита и сортировки. Интервал полуоткрытый:
начало включено, конец исключён. Архивные, завершённые и отменённые заявки
исключаются, новые и находящиеся в работе включаются.

В `dashboard.py` заменить только сборку локального списка:

```python
request_model = self.env["tucha.request"]
domain = request_model._open_requests_domain(start, end)
count = request_model.search_count(domain)
requests = request_model.search(domain, order="planned_from, id", limit=8)
```

Вычисление периода и права остаются прежними. Другие отчёты смогут пользоваться
тем же методом. Сейчас дашборд определяет сутки в UTC; переход на локальные
сутки пользователя — отдельное продуктовое решение, не скрытая часть оптимизации.

## Два теста

1. Серверный TransactionCase создаёт заявки на `start - 1 сек`, `start`,
   внутри периода, `end - 1 сек` и `end`, в состояниях new, processing,
   completed, cancelled и с active=False. Сравнивает точный набор ID результата
   `search(_open_requests_domain(start, end))` с ожидаемым. Повторяет поиск с
   `active_test=False`, чтобы проверить явное исключение архива. Проверяет,
   что `search_count` совпадает с размером набора, а повторный вызов возвращает
   независимый список. Тест выполняется с правами кандидата, без sudo.
2. После установки и после обновления модуля проверяется реальный индекс
   таблицы `tucha_request` через `pg_index`, `pg_class`, `pg_attribute` и
   `pg_am`: B-tree, ключ planned_from, не частичный и не выражение,
   `indisvalid=True`, `indisready=True`. Проверка одного лишь свойства
   `_fields['planned_from'].index` не доказывает наличие индекса в существующей БД.
   Не следует требовать Index Scan на маленькой тестовой таблице.

## Обновление существующей базы

Сначала резервная копия и пробное восстановление на стенде, фиксация текущего
времени и плана запросов. Проверить объём таблицы, свободное место, уже имеющиеся
индексы и отсутствие эквивалентного индекса под другим именем. Обновить модуль
`tucha_crm` штатным `--update=tucha_crm` и проверить реальный валидный индекс,
повторное обновление и оба теста. Метаданные Odoo и схема должны согласовываться.
Данные заявок переносить не требуется.

Обычное создание индекса при обновлении может блокировать запись. Для большой
таблицы запланировать окно обслуживания; при недопустимом простое разработать
отдельную миграцию с `CREATE INDEX CONCURRENTLY` вне транзакции, согласованным
именем индекса и проверкой невалидного остатка после сбоя. Не запускать такую
команду внутри обычного транзакционного обновления Odoo.

После обновления обновить статистику и сравнить `EXPLAIN (ANALYZE, BUFFERS)`
для обоих запросов (count и список с limit) на репрезентативном объёме и разных
периодах. Измерения проводить на стенде. Проверить неизменность результатов,
порядка, ограничения 8 записей и доступа пользователей.

## Недостатки и альтернативы

Индекс занимает место и увеличивает стоимость INSERT/UPDATE planned_from.
Он не гарантирует ускорения широкого диапазона или count. Составной индекс
(active, stage, planned_from) не выбираю без замеров: `not in` по stage может
помешать эффективному диапазону. Частичный индекс по открытым активным заявкам
может быть меньше, но привязывается к конкретному правилу и усложняет миграции.
Если B-tree недостаточно, эти варианты нужно сравнить по фактическим планам.
